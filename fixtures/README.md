# Balance fixtures

Language-neutral test cases for SplitTab's money maths. The Dart package `splittab_core` must produce **exactly** these answers. The Python reference in `reference/` is the executable version of the rules below.

```
fixtures/
  README.md                  <- this spec
  cases/NN-name.json         <- 47 cases: input trip + hand-calculated expected output
  reference/splittab_ref.py  <- reference implementation (exact arithmetic, no floats)
  reference/test_fixtures.py <- checks cases against the reference + property/fuzz tests
```

Run: `python3 -m pytest fixtures/reference -q` (278 checks at the time of writing).

## How the cases were made
1. Inputs **and expected values were worked out by hand** (they are not generated by the reference).
2. The reference was written separately and compared against them. The first run caught a real bug in the reference (payments in the direct view), not in the hand answers.
3. Extra checks need no hand-written numbers: balances sum to zero, shares add up to the expense total, the settle plan clears every balance, and the minimum number of payments is verified against a **brute-force search of every possible grouping**, plus 150 random trips.

## Case format
```jsonc
{
  "id": "16-two-payers",
  "description": "...", "tags": ["multi-payer"],
  "trip": { "home_currency": "USD", "members": ["alice", "bob", "carol", "dave"] },  // order matters (tie-breaks)
  "currency_exponents": { "USD": 2, "EUR": 2, "JPY": 0 },   // only when a foreign currency is used
  "expenses": [{
    "id": "e1",
    "amount": 10000,                        // integer minor units of `currency` (negative = refund)
    "currency": "EUR",                      // optional, defaults to home currency
    "rate": "1.10",                         // home MAJOR units per 1 MAJOR unit of `currency`; required if foreign
    "paid_by": { "alice": 6000, "bob": 4000 },   // minor units of `currency`, must sum to `amount`
    "split": { "type": "equal", "among": ["alice", "bob", "carol", "dave"] }
  }],
  "payments": [{ "from": "bob", "to": "alice", "amount": 1000 }],   // optional, home minor units
  "expected": {
    "balances": { "alice": 3500, ... },     // positive = is owed money
    "settle": { "min_payments": 3, "plan": [...] },   // plan is optional, see "Plans" below
    "direct": [{ "from": "carol", "to": "alice", "amount": 2500 }],  // optional
    "expense_home_totals": { "e1": 11000 }, // optional
    "expense_owed": { "e1": { "alice": 2500, ... } }  // optional, per-member share in home minor units
  }
}
```
Invalid input cases have `"expected": { "error": "<code>" }`. A runner checks only the keys present in `expected`.

## The rules

### Money
- All amounts are **integers in minor units** (cents, paise, yen...). No floats. Rates and percentages are **decimal strings** and must be parsed exactly (rational or decimal arithmetic).
- Minor-unit exponent per currency comes from `currency_exponents` (ISO 4217: USD 2, JPY 0, KWD 3...).

### Currency conversion (once per expense)
`home_minor = round_half_away_from_zero( amount × rate × 10^(home_exp − currency_exp) )`
Same currency as home: no conversion. Each expense converts its **total** once; paying and splitting then happen in home units. Missing rate -> `missing_rate`.

### Allocating a total (used for splits AND for payers)
Largest-remainder method on the **home** total:
1. Each share = floor(|total| × weight).
2. Leftover units go one each to the largest fractional remainders.
3. **Ties go to the member who comes first in `trip.members`** (not the order inside `among`).
4. Re-apply the sign of the total, so a refund mirrors the original expense exactly.

### Split types -> weights (must sum to 1)
| type | weight |
|---|---|
| `equal` | 1/n for each in `among` |
| `exact` | amount_i / expense amount (amounts must sum to the expense amount) |
| `percent` | percent_i / 100 (must sum to exactly 100) |
| `shares` | share_i / sum(shares) (decimal strings, ≥ 0, sum > 0) |
| `nights` | each of N nights costs 1/N of the total, split equally among members present that night; weight = sum over nights |

Payers use the same allocation, with weights paid_i / amount. Amount 0 -> nobody's balance changes.

### Balances
For each expense: `net = paid − owed` per member. Balance = sum of nets, plus payments: the payer's balance goes **up** by the amount, the receiver's goes **down**. Positive balance = is owed money. Balances always sum to 0.

### Refunds
A refund is an expense with a **negative amount**, negative `paid_by` values and the same split as the original. Allocation uses the absolute value and re-applies the sign.

### `direct` view (the explainable "who owes whom")
1. Per expense, match debtors to creditors with a two-pointer walk **in member order**.
2. Add payments as reductions of the matching debt.
3. Net each pair of members. Sort by (from, to) member order.
It always reconciles with `balances`. With a single payer the attribution is canonical; with several payers the pairing follows member order and is only an explanation.

### `settle` (fewest payments)
- A group of k members whose balances sum to zero needs k−1 payments. So the minimum is **(members with non-zero balance) − (largest number of zero-sum groups they can be partitioned into)**.
- `min_payments` is always asserted. It is computed exactly with a bitmask DP for up to 20 non-zero members (a greedy fallback beyond that).
- **Plans:** inside a group, repeatedly pay the largest remaining debt to the largest remaining credit (ties: lower member index). A fixture only pins an exact `plan` when the optimal grouping is unique (the test checks this). Otherwise only the count and the "plan clears all balances" rule apply.
- Case `36-settle-naive-greedy-not-optimal` shows why: the naive method needs 4 payments, the minimum is 3.

### Error codes
`split_sum_mismatch`, `percent_sum_invalid`, `payer_sum_mismatch`, `unknown_member`, `invalid_shares`, `night_uncovered`, `invalid_nights`, `missing_rate`, `invalid_rate`, `unknown_currency`, `empty_split`, `invalid_split_type`.

## Notes for the Dart implementation
- **Flutter web integers are JavaScript doubles (exact only up to 2^53).** Case `38-large-percent-intermediates` multiplies 5×10⁹ by a 6-decimal percentage, which exceeds that. Use `BigInt` or a rational type for intermediate products and check this case on web as well as on a phone.
- Tests should load every `cases/*.json` and compare only the keys present in `expected`. Compare `plan` and `direct` as lists of (from, to, amount).
- The reference is the tie-breaker for any ambiguity. If the reference and these rules disagree, fix the rules text.

## Rules that are product decisions (easy to change, tell me)
1. **Rounding leftovers go to the first member in trip order.** Alternative: to the payer, or rotating. Fixed order is simplest to explain, but the same person gets the extra cent every time.
2. **Conversion rounds half away from zero.**
3. **Nights split:** each night's cost is equal (total ÷ N), not weighted by room prices.
4. **Payments are in the home currency only** for now.
